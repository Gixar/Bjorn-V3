What the device does, how to set it up, and what every setting means

What Bjorn is

An autonomous network scanner and offensive-security appliance

Bjorn joins a network, maps every host on it, and then works through those hosts on its own — port scanning, fingerprinting web services, brute-forcing logins, pulling files off anything it opens — writing everything it learns into a single knowledge base (netkb.csv). It runs unattended on a Raspberry Pi with an e-Paper screen; this web UI is how you configure it and read the results.

Optional add-on modules extend it past the wired/Wi-Fi LAN: Bluetooth device recon, 802.11 access-point survey, and automatic report delivery to Telegram or email. Each one is off by default and has its own page.

Authorized use only. Bjorn actively attacks the network it is on — it brute-forces credentials and copies files. Run it only on networks and devices you own or have written permission to test. Its own MAC is auto-added to mac_scan_blacklist, but nothing else on the network is exempt unless you list it.

First run — five steps

From a fresh install to a working scan

  1. Get it on a network. On the Config page press Wi-Fi, pick an SSID and enter the password. Leave the static-IP fields blank for DHCP. Ethernet or the USB gadget (usb0, http://172.20.2.1:8000/) work too, with nothing to configure.
  2. Check the screen driver. If the e-Paper panel is blank, set epd_type on Config — auto tries every known driver, mock runs headless. To find the exact one, stop the service and run sudo python3 scripts/epd_test.py --all.
  3. Set the scan scope. portlist is the set of ports probed per host. Add anything on the network you must never touch to ip_scan_blacklist / mac_scan_blacklist before starting.
  4. Start it. Home → Start. The live console below the buttons streams what it is doing. First results appear on NetKB after the first scan pass (scan_interval, default 180 s).
  5. Turn on what you need. The optional modules are each one checkbox on their own page — see the table further down. Nothing is enabled for you.

How the cycle works

Why an action runs when it runs

  1. Scan. Every subnet Bjorn has an interface on is swept for live hosts, then those hosts are port-scanned. Results are merged into netkb.csv — hosts are never dropped, only marked alive or dead.
  2. Act, port by port. Each host's open ports decide which actions apply: 22 → SSH brute force, 445 → SMB, 80/443 → HTTP fingerprint then the web-template checks, and so on. A crack promotes the host to the matching steal action, which copies files off it.
  3. Reuse credentials. Anything cracked goes into a shared pool and is tried first against every other host and protocol (credential_reuse). One crack tends to cascade.
  4. Idle. When a pass finds nothing new, Bjorn waits out scan_interval — and during that window it gives every standalone module (BLE, Wi-Fi, SNMP, wpa-sec, reporting) a turn. Each of those throttles itself with its own interval setting.
Retries. A failed action backs off for failed_retry_delay before being tried again. A successful one is not repeated at all unless retry_success_actions is on — the point being not to re-attack a box you already own. Standalone modules are exempt from that rule; they run every idle window.

Where did my setting go? Everything for BLE, Wi-Fi, Telegram and SMTP was moved off the Config page onto the module's own page, so each module is set up next to its own results, its test button and its manual. The values are still the same keys in the same shared_config.json — saving from either page merges, never overwrites the rest.

Optional modules

All off by default — enable on the module's own page

ModuleNeedsGives you
BLE recon The Pi's built-in Bluetooth. No extra hardware. Nearby Bluetooth devices, with likely Find My / SmartTag / Tile trackers flagged.
Wi-Fi survey A second radio — a USB dongle. Never the uplink. Nearby access points and their clients: BSSID, channel, encryption, signal.
Reporting A Telegram bot token, or SMTP credentials, plus internet. The collected dataset pushed out automatically whenever it changes.
wpa-sec import A wpa-sec.stanev.org API key (wpasec_api_key on Config). Cracked Wi-Fi keys imported as low-priority NetworkManager profiles, so Bjorn can join those networks.
RustScan engine The rustscan binary (use_rustscan on Config). Much faster port discovery. Falls back to nmap automatically if missing. Time both with the Benchmark button.
Battery monitor A PiSugar-style power server (battery_monitor_enabled). Clean shutdown below battery_shutdown_percent instead of a yanked-power corruption.

Settings reference

The keys on the Config page that actually change behavior

Scanning

portlistPorts probed on every host. Comma-separated. Longer list = slower cycle.
scan_intervalSeconds between scan passes (default 180). Also the length of the idle window the standalone modules run in.
nmap_scan_aggressivitynmap timing template. -T2 is polite and quiet; -T4 is fast and loud.
ip_scan_blacklist / mac_scan_blacklistNever touched. Set these before starting on any network with something fragile on it.
use_rustscan / rustscan_full_port / rustscan_batch_sizeSwap discovery to RustScan; optionally sweep all 65,535 ports. Lower the batch size on a Pi Zero if ports start going missing.

Vulnerability scanning

scan_vuln_intervalSeconds between vulnerability passes (default 900).
vuln_scan_svService/version detection. Needed for any CVE matching to work at all.
vuln_scan_vulnersThe online vulners.nse CVE script — the heaviest step, and it needs internet.
vuln_offline_cveMatch detected versions against the bundled offline CVE database. No internet required.

Attacking

credential_reuseReplay a cracked login against every other host and protocol, tried first. On by default; the single biggest force multiplier.
bruteforce_threadsWorker threads per connector. 0 = auto (core-aware, capped at 8). Raise only if the Pi is idle.
retry_success_actions / success_retry_delayWhether to redo an action that already succeeded, and how long to wait first. Off by default.
retry_failed_actions / failed_retry_delaySame for actions that failed. On by default, 600 s.
timewait_*Per-protocol delay between attempts. Raise to stay under lockout thresholds or rate limits.
steal_file_names / steal_file_extensionsWhat the steal actions look for once a host is open.

System

manual_modeStops autonomous attacking; you drive from the Home page. Opening the manual-attack panel sets this for you.
epd_typee-Paper driver. auto to probe, mock to run with no screen.
websrvServe this web UI at all. Turning it off locks you out of everything here.
debug_mode / log_*Verbosity. Debug logging is heavy on SD-card writes — leave it off unless chasing something.
startup_delay, screen_delay, stats_ws_intervalPacing for boot, screen refresh, and the Stats dashboard push rate.

When something is wrong

Start with the diagnostic script

sudo ./scripts/bjorn_diag.sh is read-only and prints the version and the running commit, OS, SPI state, epd_type, service and process state, network, which external tools are installed, a summary of what has been found, recent errors and where every file lives — including when Bjorn will not start at all. Add --short for a quick pass or --save to write a timestamped copy under data/output/. Details are in TROUBLESHOOTING.md in the repository.

Read the top of the report first — it says how many commits behind the checkout is. A report from stale code describes a device you may have already fixed. Config secrets are redacted, so it is safe to paste into an issue.
Nothing on the e-Paper screenWrong epd_type. Stop the service first (it holds the GPIO pins), then sudo python3 scripts/epd_test.py --all and set the driver that actually renders.
Web UI unreachableConfirm the Pi's IP and that the service is running; the UI is on port 8000. If the Pi is plugged into a host over USB, try http://172.20.2.1:8000/.
No hosts foundBjorn scans the subnets of its own interfaces. Check it actually joined the network, and that the target range is not blacklisted.
A module does nothingEvery module is off until enabled, and each throttles itself with an interval. Enable it on its own page, then give it one idle window.
Scans feel too slowShorten portlist, raise nmap_scan_aggressivity, or enable use_rustscan and compare with the Benchmark button on Config.
